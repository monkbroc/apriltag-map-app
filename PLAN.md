# AprilTag Map App — Implementation Plan

This plan implements [REQUIREMENTS.md](REQUIREMENTS.md). Each phase ends in a state
that builds, passes its tests, and can be committed on its own. Pure TypeScript logic
(Phase 3) comes before the native module (Phase 5), so most of the app can be built
and tested on Windows before any device work starts.

> **Dev machine note:** The primary machine is Windows. Android can be built and run
> locally. iOS native builds need macOS: use `npm run build:ios:cloud` (EAS Build) from
> Windows, or a Mac for `npm run build:ios` and for debugging the Swift module.

---

## Phase 0 — Tooling

1. Install **Node.js LTS** (22.x). Use **npm**, with `package-lock.json` committed.
2. Install **Git** and the **GitHub CLI** (`gh`). Run `gh auth login`.
3. Install **Android Studio**, with:
   - Android SDK Platform 35 and Build-Tools
   - NDK (the side-by-side version required by the Expo SDK)
   - CMake
   - JDK 17

   Then set `ANDROID_HOME` and add `platform-tools` to `PATH`.

4. Install the **EAS CLI**: `npm i -g eas-cli`, then `eas login`. Create an Expo account if needed.
5. Apple Developer Program membership (needed to sign iOS builds for internal distribution or TestFlight).
6. Prepare test devices:
   - an ARCore-supported Android phone, with USB debugging enabled
   - an ARKit-capable iPhone, registered for internal distribution with `eas device:create`
7. _(Optional, for local iOS builds)_ A Mac with Xcode and CocoaPods.

## Phase 1 — Project scaffold

1. Initialize the repository: `git init`, a `.gitignore`, and `README.md`. Create the GitHub repo with `gh repo create`.
   - `android/` and `ios/` are generated by `expo prebuild`, so they go in `.gitignore`.
2. Create the app: `npx create-expo-app@latest . --template blank-typescript`, then pin the Expo SDK exactly.
3. Add the core dependencies, using `npx expo install` so the versions match the SDK:
   - `expo-router`
   - `expo-dev-client`
   - `expo-file-system`
   - `expo-sharing`
   - `expo-document-picker`
   - `expo-clipboard`
   - `expo-crypto` (for UUIDs)
   - `react-native-svg` (for the 2D map)
   - `zustand` (for app state)
   - `zod` (for schema validation)
4. Add the dev dependencies:
   - `typescript` (strict)
   - `eslint` with `eslint-config-expo`
   - `prettier`
   - `jest` with `jest-expo`
   - `@testing-library/react-native`
5. Add the npm scripts `lint`, `typecheck`, `test`, `test:ci` (which runs with coverage), and `format`. The build scripts are added in Phase 2.
6. Create the folder structure:

   ```
   src/app/                  # expo-router screens (Expo SDK 58 convention)
     index.tsx               # library (home)
     sets/[id]/index.tsx     # set detail (Map | Table | JSON tabs)
     sets/[id]/edit-tag.tsx
     scan/new.tsx            # fresh scan setup
     scan/session.tsx        # AR scanning (?refine=<setId> for refine mode)
     scan/align.tsx          # reference tag poses + alignment residuals
     scan/compare.tsx        # refine comparison
     scan/review.tsx         # fresh-scan review
     import.tsx
     licenses.tsx
   src/
     core/                   # pure TS, no RN imports, ≥80% coverage
       config.ts             # all tuning constants
       math/                 # mat4, quaternion, euler
       fmap/                 # schema, parse, serialize, validate
       scan/                 # observation filtering + averaging
       align/                # 4-DoF yaw + translation fit
       diff/                 # per-tag deltas, % change, classification
       merge/                # replace-all-seen merge
     data/builtinSets/       # frc2026.fmap.json + index.ts registry
     storage/                # one JSON file per set
     state/                  # zustand stores (library, scan session)
     components/             # FieldMap, TagTable, JsonView, DeltaRow, HUD...
     native/                 # TS wrapper around the Expo module
   modules/apriltag-ar/      # local Expo Module (Swift/Kotlin/C)
   scripts/                  # build-android.mjs, convert-wpilib-layout.ts
   *.test.ts colocated
   ```

7. Set up the Expo Router layout, theming, and an empty screen for each route. Check that the app runs on Android with `npx expo run:android`.
8. Commit: **"Scaffold Expo app"**.

## Phase 2 — CI and build commands (set up early so that every later phase is checked)

1. `.github/workflows/ci.yml`:
   - Triggers on `pull_request` and on `push` to `main`.
   - Uses `concurrency: ci-${{ github.ref }}` with `cancel-in-progress: true`.
   - Runs on `ubuntu-latest`: `actions/checkout@v4`, then `actions/setup-node@v4` (Node 22, `cache: npm`), then `npm ci`, then `npm run lint`, then `npm run typecheck`, then `npm run test:ci`.
   - Uploads the coverage report as a build artifact.
2. `.github/workflows/eas-build.yml`:
   - Triggers on `v*` tags (production profile) and on `workflow_dispatch`, with a `profile` input (`preview` or `production`) and a `platform` input (`android`, `ios`, or `all`).
   - Skips the job when there is no `EXPO_TOKEN`: set `env: EXPO_TOKEN: ${{ secrets.EXPO_TOKEN }}` at job level, then guard the steps with `if: env.EXPO_TOKEN != ''`.
   - Steps: `expo/expo-github-action@v8` (with `eas-version: latest` and `token`), then `npm ci`, then `eas build --platform <platform> --profile <profile> --non-interactive --no-wait`.
3. `eas.json`, with three profiles. None of them submit to a store.
   - `development`: dev client, internal distribution
   - `preview`: internal distribution; Android builds an APK, iOS builds an ad hoc `.ipa`
   - `production`: same as `preview` but with a release version and `autoIncrement`. An iOS production build can be uploaded to TestFlight for internal testing.
4. **Local build commands** (R-8.3):
   - `scripts/build-android.mjs`:
     - runs `npx expo prebuild --platform android`
     - then runs `gradlew.bat assembleRelease` on Windows, or `./gradlew assembleRelease` elsewhere, inside `android/`
     - then prints the APK path (`android/app/build/outputs/apk/release/app-release.apk`)

     Sign the release with a keystore set in `android/gradle.properties`, loaded from environment variables. Without one, fall back to the debug keystore, which is fine for sideloading during development.

   - npm scripts:
     - `"build:android": "node scripts/build-android.mjs"`
     - `"build:ios": "eas build --platform ios --profile preview --local"` (macOS + Xcode only; writes the `.ipa` to the project root)
     - `"build:ios:cloud": "eas build --platform ios --profile preview"`
     - `"build:android:cloud": "eas build --platform android --profile preview"`
   - Document all four in the README, including how to install the result:
     - Android: `adb install <apk>`
     - iOS: the EAS install link or QR code, or Apple Configurator
5. Run `eas init` to link the project ID into `app.json`. Add the `EXPO_TOKEN` repository secret with `gh secret set EXPO_TOKEN`.
6. Set up branch protection on `main` that requires the CI workflow to pass.
7. Commit: **"Add CI, EAS build workflow, and local build scripts"**.

## Phase 3 — Core logic in pure TypeScript (test-driven)

Write the tests first, in each module. Jest runs these in Node with no React Native.

1. **`core/config.ts`**: all tuning constants:
   - `MIN_OBSERVATIONS`
   - the acceptance thresholds
   - the color thresholds
   - `RMS_WARN_M`
   - `DEFAULT_TAG_SIZE_MM`
2. **`core/math`**
   - Types: `Vec3`, `Mat3`, `Mat4` (row-major, 16 values), and `Quat`.
   - Operations: compose, invert, transform a point, matrix ↔ quaternion, matrix ↔ Euler ZYX (in degrees), re-orthonormalize (through a quaternion round trip), and the geodesic angle between rotations.
   - Tests: round trips, identity, gimbal edge cases, and checks that results stay orthonormal.
3. **`core/fmap`**
   - A `zod` schema covering R-3.1 and R-5.9.3.
   - `parseFmap(text)` returns `{ok, set, warnings} | {ok:false, errors}`.
   - `serializeFmap(set)` follows the formatting rules in R-3.1.7 and R-3.1.8.
   - Tests:
     - a golden-file round trip of the FRC 2026 built-in
     - each rejection case
     - silent re-orthonormalization of rotations that are within tolerance
4. **`core/scan`**
   - An observation type: `{tagId, T_world_tag, decisionMargin, pixelSize, viewAngleDeg, timestamp}`.
   - The acceptance filter from R-5.3.3.
   - Averaging from R-5.3.4: mean position, and a sign-aligned, normalized quaternion mean.
   - Tests: synthetic noisy observations. The recovered pose must fall within tolerance.
5. **`core/align`**
   - A fixed change of axes from the AR world frame (Y up) to a Z-up frame.
   - `fitYawTranslation(pairs)`: closed-form 2D least squares on XY (yaw from atan2 of the summed cross and dot products of centered points), plus the mean Z offset.
   - `fromSingleTag(scanPose, refPose)`: yaw and translation from one tag.
   - `align(scanned, reference, excludedIds)` chooses between the two (R-5.4.1) and returns `{T_field_world, rmsResidual, perTagResidual}`.
   - Tests:
     - recover a random yaw + translation applied to a synthetic field, with and without noise
     - the single-tag case
     - the no-shared-tags error
     - excluding a tag changes the fit
6. **`core/diff`**
   - `diffSets(reference, scanned)` returns rows with status, ‖Δt‖, the % change (with the near-origin rule), the rotation delta, and a classification from the `config.ts` thresholds.
   - Tests: each status, the % edge cases, and the threshold boundaries.
7. **`core/merge`**
   - `mergeReplaceAllSeen(reference, scanned, minObs)` follows R-5.5.4.
   - Tests: unseen tags are kept, new tags are added, and size and `unique` are preserved.
8. Coverage gate: set `coverageThreshold` for `src/core/**` at 80% in the Jest config.
9. Commit after each module.

## Phase 4 — Data, storage, state, and the non-AR UI

1. **Built-in FRC 2026 set**
   - Get the official 2026 layout: the WPILib `2026-*.json` field layout and/or Limelight's published FRC 2026 `.fmap`.
   - Write `scripts/convert-wpilib-layout.ts`. It:
     - changes the origin from the blue-alliance corner to field center (subtract half the field length and width)
     - converts the quaternions to row-major 4×4 matrices
     - sets size = 165.1 and family = `apriltag3_36h11_classic`
     - writes `src/data/builtinSets/frc2026.fmap.json`, with the field dimensions as metadata
   - Cross-check against Limelight's published map, if one is available. Add a unit test that freezes a few known tag poses (R-3.3.2).
   - Write the registry `index.ts`.
2. **`storage/`**
   - `TagSetRepository` with `list` (which reads the `tagsets/` folder), `get`, `create`, `update`, and `delete`, on top of `expo-file-system`.
   - Each file has a `schemaVersion` of 1.
   - No test of its own: it is covered by the import screen test through an in-memory mock of `expo-file-system`.
3. **`state/`** — two zustand stores:
   - `useLibrary` (sets, plus CRUD that calls the repository)
   - `useScanSession` (mode, reference set, observations, aggregated tags, alignment result, excluded tag IDs)
4. **Components**
   - `FieldMap`: a static SVG with a `viewBox` that fits the field. It draws:
     - the field outline
     - tag arrows and ID labels
     - tap targets on each tag
     - the old/new comparison overlay
   - `TagTable`
   - `JsonView`
   - `DeltaRow`
   - `NumberField` (with validation)
   - `ConfirmDialog`
5. **Screens**
   - Library: the list, plus the Open, Refine, Rename, Delete and Export actions. Refine is wired up in Phase 6.
   - Set detail: the Map, Table, and JSON tabs.
   - Tag editing:
     - size, pose, add, and delete, all working on a draft
     - editing a built-in set first asks for a name and creates a user copy (R-4.2)
   - Import: the document picker, then validation, then a preview, then the name prompt.
   - Export: serialize, write to cache, then open the share sheet.
   - Licenses.
6. **Component test** (React Native Testing Library): the import screen, covering a valid file and the error display for an invalid one.
7. Commit after each screen. At this point the app is useful without AR: it can view, edit, import, and export sets.

## Phase 5 — Native AprilTag + AR Expo Module

1. Scaffold the module with `npx create-expo-module@latest --local apriltag-ar`. This creates `modules/apriltag-ar` with iOS and Android targets.
2. **Shared C**
   - Vendor the AprilTag 3 sources (pinned to a release tag) into `modules/apriltag-ar/cpp/apriltag/`.
   - Keep only the core detector, `tag36h11`, and `apriltag_pose`.
   - Add a thin C wrapper, `detect(gray, w, h, stride, fx, fy, cx, cy, tagSizeM) → [ {id, corners, R, t, decision_margin, hamming} ]`, that reuses a single detector instance.
3. **iOS (Swift)**
   - Add the C sources to the podspec, with a module map or bridging header.
   - Run an `ARSession` with `ARWorldTrackingConfiguration` and show its view through an `ARSCNView`-backed Expo view component (`ApriltagArView`).
   - On a background queue, throttled to the target rate:
     - take the Y plane of `capturedImage`
     - read `camera.intrinsics`, scaled to the processed resolution
     - run detection
     - compose `T_world_tag = camera.transform · T_cam_tag`
   - Convert from the AprilTag camera frame (x right, y down, z forward) to the ARKit camera frame (x right, y up, z backward).
   - Send these events to JS:
     - `onObservation`, one per detected tag, with its corners for the overlay
     - `onTrackingState`
     - `onError`
4. **Android (Kotlin)**
   - Add the ARCore dependency, a `<meta-data com.google.ar.core=optional>` entry, and the camera permission.
   - Use CMake/JNI for the C library.
   - Run an ARCore `Session` and render to a `GLSurfaceView` behind the Expo view.
   - Use `frame.acquireCameraImage()` (YUV, taking the Y plane), `camera.imageIntrinsics`, and `camera.pose`, and do the same frame conversion and composition as on iOS.
   - Handle the AR install/update flow with `ArCoreApk.requestInstall`.
5. **Config plugin**
   - Add camera usage strings to `Info.plist`. Don't require ARKit as a device capability (R-2.4).
   - Add the Android manifest meta-data and permissions.
6. **TS wrapper (`src/native/`)**
   - Typed events.
   - An `isSupported()` check.
   - A mock implementation that is used under Jest and on unsupported devices, which replays recorded observation JSON.
7. **Manual device checklist** in `docs/device-test.md` (this replaces native unit tests):
   - Point the camera at a tag at a known distance straight ahead. Check that the translation is about (0, 0, −d) in the ARKit camera frame.
   - Check that the correct ID is detected for a few printed tags.
   - Walk between two tags a known distance apart, and check the measured distance.
8. Build dev clients with `npx expo run:android` locally, or `eas build --profile development --platform ios` for iOS, and run the checklist on real devices.

## Phase 6 — Scan flow UI

1. Scan entry points (both check permissions and AR support first):
   - `scan/new` (from the global "New scan"): fresh scan, starting with no tags.
   - **Refine** action on the library row and on the set detail screen: goes straight to `scan/session?refine=<setId>`, with that set as reference and baseline.
2. `scan/session`:
   - `ApriltagArView` with an SVG overlay for tag outlines and IDs
   - the HUD (tracking state, counts, and chips colored by observation count)
   - Pause/Resume and Finish
3. Observations are fed to `core/scan` averaging in `useScanSession`, throttled so the UI updates at most 10 Hz.
4. `scan/align`:
   - Refine mode: runs the automatic fit.
   - Fresh mode: the user picks reference tags and types in each one's field pose (default: the origin with identity rotation).
   - Shows the RMS and per-tag residuals. Each tag in the list has a checkbox to exclude it, and unticking one refits.
5. `scan/compare`:
   - the summary header
   - the delta rows
   - the `FieldMap` comparison overlay
   - Save as new, Overwrite (disabled for built-ins, with confirmation), and Discard
6. `scan/review` (fresh mode): the map, the table, and Save as new.
7. Tests:
   - A component test for `scan/compare`, driven by fixture data: the rows, the statuses, and Overwrite disabled for a built-in set.
   - A Jest test that replays a recorded refine session through the mock native module. It goes through averaging, alignment, diff, and merge, then checks the resulting set.

## Phase 7 — Validation on a real field

1. Record scans of an FRC 2026 field (or a partial practice field with measured tag positions). Save the raw observation logs in a debug-only export so that they can be replayed in tests.
2. Measure against R-7.1 (≤ 3 cm RMS and ≤ 1.5°). Tune the constants in `config.ts` and the detector parameters.
3. Profile detection rate and UI frame rate on mid-range devices (R-7.2), and adjust the decimation and thread count.
4. Accessibility pass (R-7.3).
5. Load the exported `.fmap` onto a Limelight and check that MegaTag localization gives sensible robot poses.

## Phase 8 — Internal release

1. App icon and splash screen. Bump the version.
2. Tag `v1.0.0`. The EAS production build runs from CI. Alternatively, build locally with `npm run build:android` and `npm run build:ios`.
3. Distribute:
   - Android: share the APK for sideloading.
   - iOS: share the EAS internal-distribution install link with registered devices, and/or upload the build to TestFlight for internal testers (`eas submit --platform ios` to TestFlight only, no App Store review).
4. Write the README:
   - features
   - the coordinate conventions
   - build and install commands
   - how to add a new built-in season
   - how to run the tests
